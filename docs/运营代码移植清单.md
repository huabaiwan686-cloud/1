# 运营代码 vs 重构版：值得移植的功能清单

> 对比对象：服务器 `/opt/content-platform`（Flask + SQLite 单体，线上运行中）
> 分析日期：2026-10-06

---

## 🔴 P0 — 强烈建议（业务核心，缺了有实质风险）

### 1. 循环重发变体（防 TG 判重）
- **说明**：循环上架重发时，对文本只做空白字符微调（不改词句/链接），图片做随机微裁切（0.3%~0.8%）+ 亮度 ±0.5% + JPEG 质量 90~93 + 随机 comment，视频用 ffmpeg 微裁切 + 随机 CRF 重编码。每次循环文件 hash 都不同，躲 Telegram 重复内容检测。临时文件发送后删除，启动时清理死进程残留。
- **位置**：`backup-media-speed-20261004-181248/transient_media.py:1-93`
- **我方现状**：缺失。我们的循环上架每次发送完全相同的文件，长期循环极易被 TG 判定为 spam/重复。
- **移植建议**：在 `publisher.py` 的循环发送路径加 `variation` 开关；图片用 PIL 微调、视频用 ffmpeg（如已安装），处理图放内存或临时文件，发送后清理。

### 2. 下架自动删帖 + 发送回执
- **说明**：每次发送记录 `receipts` 表（content_id, channel_id, bot_id, chat_id, message_id, part, account_id）。资料归档/下架时自动入 `removals` 队列，worker 逐条调 Bot API `deleteMessage` 或协议号 `revoke` 删除已发消息，记录成功/失败数。
- **位置**：`history.py:1-67`
- **我方现状**：缺失。我们只有 TaskLog 文本记录，没有 message_id，资料下架后频道里的帖子删不掉。
- **移植建议**：`send_listing_set` 返回 message_id → 新建 `PublishReceipt` 表；Note offline/archive 时入删除队列，worker 复用现有 Bot/协议号通道删除。

### 3. 发布分批策略细节
- **说明**：① 超 10MB 的图片不进相册，单独以 `document` 形式发送；② 单张媒体用 sendPhoto/sendVideo 而不用 mediaGroup；③ caption 只放第一批并截断 1024 字符，超长正文按 4000 字符分段用 sendMessage 补发；④ 批次之间 `sleep(1)`；⑤ 全局 `SEND_LOCK` 串行化发送。
- **位置**：`app.py:742-772`
- **我方现状**：有但简陋。我们的 `send_listing_set` 直接把最多 10 个媒体打包，不处理超大图、超长文本分段更粗糙。
- **移植建议**：在 `publisher.py` 照抄分批逻辑；`SEND_LOCK` 可用 `phone_lock` 思路按 Bot 维度加锁。

### 4. 验证视频硬性校验
- **说明**：发布前强制校验验证视频必须且只能是 1 个 MP4，否则拒绝发布（`len(verification)!=1 or mime!='video/mp4'`）。
- **位置**：`app.py:740`，`app.py:483-488`（`publish_material_error`）
- **我方现状**：缺失。我们不校验验证视频数量和格式，传错了到发送时才报错。
- **移植建议**：在笔记发布/审核通过入口加校验，前端上传页也限制。

### 5. 智能频道推荐（规则自动匹配）
- **说明**：按规则自动匹配发布频道：关键词、标签、城市/省份（从正文"城市：北京"这类标注行解析）、价格区间（解析"价格：￥500"）。无规则命中时回退到默认频道。
- **位置**：`app.py:421-457`（`rule_matches` + `content_recommendations`）
- **我方现状**：缺失。我们的笔记 `channel_ids` 全靠手动选。
- **移植建议**：新建发布规则表（keyword/tag/city/province/price_min/price_max → channel_ids），审核通过页加"智能推荐"按钮一键填充。

## 🟡 P1 — 高价值（运营效率/风控）

### 6. 自动转发（协议号源群→目标群）
- **说明**：协议号监听源群/频道新消息，按关键词过滤后 `forward_messages` 到目标群。相册按 `grouped_id` 聚合；边界不完整相册等待 3 秒；`relay_deliveries` 表做幂等；发送中服务重启则自动停用规则并要求管理员人工确认后才恢复（防重复转发）。
- **位置**：`relay.py:1-121`
- **我方现状**：缺失。我们有采集（入库审核），但没有这种"监听即转发"的轻量链路。
- **移植建议**：可作为采集的补充形态：RelayRule 表 + worker 定时 poll，复用现有 Telethon 共享连接。

### 7. 双向客服消息中继
- **说明**：客户私聊 Bot → `forwardMessage` 到客服群并建 `support_links` 映射；客服在群里回复该消息 → `copyMessage` 回传给客户。Bot 用 getUpdates 轮询（2 秒间隔），`bot_events` 表按 (bot_id, update_id) 去重，状态机 waiting→processing→done/uncertain，检测 Webhook 冲突。
- **位置**：`inbox.py:1-128`
- **我方现状**：有表无魂。我们的 `two_way_bots` 只建群+绑记录，没有消息中继逻辑。
- **移植建议**：补 Bot getUpdates 轮询 worker + 转发/回复映射逻辑，这是"双向机器人"名称的真正含义。

### 8. 关键词监控告警（通知管理员）
- **说明**：与地区 DM 分开的另一套监听：群聊出现配置关键词时，直接用 Bot 给管理员发告警消息（含群名+文本前 3500 字）。关键词最多 100 个，管理员 ID 最多 30 个。
- **位置**：`inbox.py:14-45`
- **我方现状**：缺失。我们的监听只给触发者发 DM，没有给管理员的告警通道。
- **移植建议**：在 ListenPlan 加 `alert_admin` 模式，或独立的 MonitorKeyword 表，命中后经 Bot DM 管理员。

### 9. 图片感知去重（dHash + 颜色距离）
- **说明**：去重不止比 SHA256：图片算 9×8 梯度 dHash，汉明距离 ≤ 阈值（可配 0~20）且平均颜色差 ≤30 即判相似；文本去重是去空白+大小写折叠后精确比对。
- **位置**：`extensions.py:167-213`
- **我方现状**：简陋。我们只有文本精确比对（`_text_duplicate`），图片靠采集时的唯一约束，换个压缩率就绕过。
- **移植建议**：采集入库和上传时加 dHash 指纹列，阈值做成采集规则的可配项。

### 10. 循环顺序打乱（cycle_shuffle）
- **说明**：频道的循环任务到期时，如果开了 `cycle_shuffle`，worker 从到期的循环任务里随机挑一个发，而不是按时间 FIFO，避免发送顺序完全可预测。
- **位置**：`app.py:877-881`
- **我方现状**：缺失。我们的 worker 按 `scheduled_at` 严格排序。
- **移植建议**：Channel 加 `cycle_shuffle` 开关，worker 取任务时对同频道的到期任务随机选择。

## 🟢 P2 — 体验/运营向（值得做，不紧急）

### 11. 协议号 Session 导入
- **说明**：支持导入现成的 Telethon session（SQLite 文件或 StringSession 字符串），带校验：auth_key 必须 256 字节、服务器 IP 必须是公网、手机号必须一致。5MB 大小限制。
- **位置**：`accounts.py:59-77`
- **我方现状**：缺失。我们只支持手机验证码登录，迁移旧号很麻烦。
- **移植建议**：tg.py 加 `/import` 接口，复用其校验逻辑，session 转 StringSession 加密入库。

### 12. 扫码登录（完整实现）
- **说明**：Telethon `qr_login()` 生成二维码，前端轮询状态；扫码后校验扫码账号手机号与填写的一致；处理 `SessionPasswordNeededError`（二级密码）、FloodWait、120 秒过期。
- **位置**：`account_features.py:24-57`
- **我方现状**：空壳。我们的 tg.py docstring 提了扫码但没实现，前端审计也标了"待接入"。
- **移植建议**：照抄其 `qr_worker` 模式，用我们的 Fernet 加密存 session。

### 13. 文字水印 / 二维码水印
- **说明**：水印不止抠图：文字水印支持 single/grid/diag/corners/center 五种布局、旋转角度、间距、数量（最多 100）、描边；还支持叠加二维码（自定义文本）。水印结果按 `watermark-<sha256>.jpg` 缓存，不重复渲染。
- **位置**：`extensions.py:24-103`
- **我方现状**：缺失。我们只有 原图/替换背景/背景虚化（混淆扰动已内置为处理层，不再是独立模式），没有文字水印。
- **移植建议**：作为新的 `anti_scan_mode` 选项加入图片处理管线，缓存键用原图 hash + 配置 hash。

### 14. 个人水印设置（按作者覆盖）
- **说明**：每个采集员可保存自己的防扫图配置（`user_watermark` 表），发布时作者个人配置覆盖全局；频道也可单独开关水印。三级优先级：个人 > 频道 > 全局。
- **位置**：`personal_watermark.py:1-35`，`app.py:736`
- **我方现状**：缺失。我们只有全局 + 频道两级。
- **移植建议**：User 加 `watermark_config` JSON 字段，`matt_for_publish` 时按优先级合并。

### 15. 批量删除未使用素材（安全确认流程）
- **说明**：预览 → 生成带 5 分钟过期的签名 token（含查询快照 digest）→ 确认时校验 token 且快照无变化才执行；文件先移入 staging 目录，DB 提交成功后才真删，失败回滚恢复。
- **位置**：`bulk_files.py:1-52`
- **我方现状**：缺失。我们的素材删除是单删直删。
- **移植建议**：素材库加"清理未使用"按钮，照抄预览-签名-确认三段式。

### 16. 采集通配符替换
- **说明**：文本替换规则支持 `wildcard` 模式，`*` 转为 `\d*` 正则（比如把"微信号 `abc123`"里的数字抹掉）。
- **位置**：`collection.py:5-17`
- **我方现状**：缺失。我们的 `text_replace` 是纯字符串替换。
- **移植建议**：采集规则加 `match_mode` 字段，wildcard 时按其正则转义逻辑处理。

### 17. 发布间隔可配 + 单任务串行
- **说明**：worker 一次只处理一个 job（`BEGIN IMMEDIATE` 抢锁），`send_interval` 可配（默认 5 秒），空闲时 sleep 2 秒。发送频率可控，防封。
- **位置**：`app.py:872-895`
- **我方现状**：部分有。我们的 worker 60 秒一轮，一轮内串行发完，没有任务间间隔。
- **移植建议**：GlobalSetting 加 `send_interval`，`_send_to_channels` 循环内按间隔 sleep。

---

**一句话总结**：运营代码最值得学的不是功能广度，而是**风控细节**——循环变体防判重、下架删帖、发送回执、分批策略、uncertain 状态人工确认，这些都是长期运营踩坑沉淀下来的，我们的重构版目前是"能跑通"但"不经跑"。建议优先移植 P0 的 5 项。
